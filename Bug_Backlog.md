# Bug Backlog

Open defects and known risks. **P1 items are surfaced at every `/startup`.**

Rows are ordered by priority, highest first.

Priorities:

- **P1** — blocks the daily pipeline. Data is being lost, the ring isn't syncing, or the
  dashboard is wrong. Fix before new features.
- **P2** — degrades something that still works. Fix when convenient.
- **P3** — annoyance, cosmetic, or cleanup. Fix when idle.
- **RISK** — not a defect yet. A known failure mode that will become P1 if unhandled.

Entry format: one row per item. Add the date found; add the date closed and move the row
to Closed rather than deleting it — a fixed bug is video material.

| R-018 | **P1** | 2026-08-17 | hub / systemd | **No hub service survives a reboot. The home directory is eCryptfs-encrypted.** Confirmed: `/home/.ecryptfs/warlock/.Private on /home/warlock type ecryptfs` — the whole home, not a `~/Private` subfolder. It decrypts only on interactive login, so at boot the systemd user manager starts, reads an empty `~/.config/systemd/user/`, finds no units, and reaches `default.target` in **471 ms** having started nothing. `Linger=yes` is set and is irrelevant. Found by rebooting: the phone got **502** from Tailscale Serve — Serve alive, `127.0.0.1:8000` dead — and `list-timers` showed no ring timers. The tell was `systemctl --user status ring-dashboard` reporting `loaded; enabled` while `list-units --all` did not list it: `status` re-read the file *after* SSH login decrypted the home, and `WantedBy=` was empty because systemd's in-memory graph was built at boot from an encrypted directory. Corroborated in the same boot log by `wireplumber` failing with `Permission denied` on `/home/warlock/.local/state`. **`enable-linger` cannot fix this, and neither can plain system units** — `WorkingDirectory` and `.venv/bin/uvicorn` are themselves inside the encrypted home. **Fix (session 8): move repo, venv and data to `/srv/ravenx`, convert all four units to system units with `User=warlock`.** **Worse than first written, confirmed 2026-08-20.** The failure is not limited to boot. eCryptfs unmounts the home when the last login session closes, so *any* scheduled run while nobody is logged in dies with **`status=203/EXEC`** — systemd cannot execute `.venv/bin/python` because the path does not exist from its point of view. Both the 08:00 and 14:00 slots failed that way on 2026-08-20, and a manual run at 20:46 then stored **122 new of 122 parsed** samples across 08-18..08-21 — every one previously unstored. **Nothing was lost only because the ring's onboard buffer (>=9 days) backfilled it**, which is the concrete payoff of having measured that depth. Left alone past the buffer window this becomes permanent data loss. Stopgap until the migration: stay logged in, or start the units by hand and run `systemctl --user start ring-sync.service` while connected; they run fine once the home is decrypted. |
